# One brief to a playable preview

The default production workflow is `.github/workflows/ice-production.yml`.
An operator adds one request file containing `{"version":1,"job":"studio/production/jobs/living-plant-01.json"}` under `studio/production/requests/` on main. That is the complete dispatch.

The Producer chooses relevant departments from the 25-role roster. Each selected specialist contributes actual multi-file product changes in a shared virtual workspace; the Integrator sees and owns their combined implementation. Role expertise is not a one-file ownership restriction. Layouts, coordinates, artwork, animations, UI, product modules and their consumers can evolve together.

The workflow then runs unit/behavior checks, a portable full Chrome touch playthrough and independent outcome checks. Actual screenshots and the approved art reference go to the independent visual director. Failed tests or visual feedback automatically become the next integrator repair brief. One job has an initial build plus up to five repairs, sharing one cumulative ledger allowance. After a visual rejection, the producer reassigns art and environment work to implementation specialists; the integrator does not work alone. Art leads and the integrator use the already approved stronger coding model with medium reasoning. A continuation can carry forward an accounted previous candidate after proving that the base product has not changed; previously billed calls are not charged again. The final trusted publisher promotes only the exact accepted package and deploys its portable game directory. The operator does not dispatch individual departments, copy their files, open each PR, integrate their patches or deploy each stage.

The existing $2/run, $5/day and $50 experiment caps remain unchanged. Every generation/review call is reconciled from provider usage. Unknown billing retains its reservation and stops further spending. Work is on demand; no schedule or unlimited task loop is added.

Executable failures return the failed test names, assertion messages and locations to one relevant repair department and then the integrator. Complete command logs are archived separately so verbose passing output and large object diffs cannot hide an early failure or consume the next repair prompt. Visual rejections still return to complementary creative departments. A request that cannot fit its reserved budget ends the job without purchasing another planning pass. A provider rejection stops requests; unknown usage keeps its allowance reserved for reconciliation.

Provider-key jobs only read inert text/images and return data. Generated code executes in separate jobs without provider/publishing credentials. The publisher cannot execute candidate code or edit CI/budgets from model output. Product patches are restricted to game/content/asset/product-test directories, with no symlink or traversal escape. A non-fast-forward main update is refused if another actor changed the base. All outcomes preserve code, test evidence, screenshots, review feedback and a production history record.

The public SCENES/VIEWPORT/drawScene and PlatformPlayer interfaces remain observable by the independent gameplay harness. These are QA interfaces, not fixed geography. For a physical staircase, `scene.stairs` records `{x,y,w,h,direction:"left"|"right"}`: `y` is its upper floor and `y+h` its lower floor. The actual collision surfaces and walking behavior must support that route. The job verifier walks it; a metadata-only staircase cannot pass.

Physical-phone feel and final creative judgment remain observations made by the player. A failed candidate never replaces the accepted preview. If all finite attempts fail, the job ends with a concrete report rather than requesting a new instruction for every department.

The legacy single-module workflow remains available for deliberately small repairs; it is not the default game-production pipeline.
