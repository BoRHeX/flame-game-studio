# ADR-0007 — delegated game production and verified preview promotion
Status: ACCEPTED
Date: 2026-11-12
Authority: explicit user instruction to automate the studio rather than supervise each action.

The user rejected excessive preservation constraints and incremental cosmetic output. A production job now grants creative authority across the product: locations, scene coordinates, composition, artwork, animations, UI and coordinated module changes can evolve. Old work-order file limits, original four-floor templates, fixed-location assertions and department-only ownership rules are superseded for these jobs. The core game's observable flame/process causality, playable interactions, recoverable saves and mobile usability remain outcomes to test rather than frozen implementations.

One job starts the entire pipeline: producer-selected departments -> shared implementation -> integration -> independent executable checks -> screenshot/reference review -> bounded automatic repair -> verified preview promotion and deployment. The user has explicitly requested this automation; fresh operator approval is not required for each department, integration or tested development-preview promotion. This is not authorization to modify the separate BoRHeZ Games Studio experiment, publish a store release, change account credentials or increase the established budget caps.

The existing 25-role roster supplies expertise. Legacy individual profiles remain usable by the legacy small-task runner; their historical one-file deliverables do not limit the active production job. New job prompts carry that precedence explicitly. The previously repeated layouts and exact chamber/exhaust coordinates are not acceptance criteria. Physical reachability, actual staircase traversal and real rendered progress are.

Model generation and image-based QA remain separate from execution and publishing credentials. All attempts share one durable reservation. The trusted publisher records provenance, refuses a stale base, promotes the exact tested package and deploys it within the same workflow, so GitHub's self-trigger suppression cannot leave a merged but undeployed build.
